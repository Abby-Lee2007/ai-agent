# AI Banking Agent · 智能银行代理系统

> 合并版 v3：当前业务、风险问卷、确认流程、异常量化、OCR 防护、网页上传和部署能力的完整集合。

> 2026 FinTechathon 深圳国际金融科技大赛（微众银行金融科技大学生挑战赛）· 人工智能国内赛道
>
> 赛题：构建 AI Banking Agent 智能银行代理系统
>
> **本系统为赛事原型 Demo：所有账户、交易、理财与卡片数据均为模拟数据，不接入任何真实银行系统、征信或资金接口，不可用于真实银行业务。**

## 一、项目简介

用自然语言对话完成银行日常业务：转账、看账单、买理财、管卡片、管订阅，
以及跨场景的主动服务（识别重要日期并自动安排）。

技术上不是"把 LLM 接上几个函数"的演示，而是一套完整的分层 Agent 架构：

```
自然语言
  -> 意图识别（大模型优先 / 规则兜底）
  -> 槽位补全（多轮对话追问）
  -> 任务规划（单步 or 跨工具多步计划）
  -> 风控校验（限额 / 二次确认 / 身份验证 / 拦截）
  -> 工具执行（35 个银行业务工具）
  -> 自然语言应答 + 工具调用轨迹
```

### 三个技术取舍

**不依赖任何第三方库也能跑。** 全部用 Python 标准库实现（HTTP 调用用 `urllib`），
`python run.py` 直接启动，断网也能完整演示六大场景。这样答辩现场不会因为装包失败翻车。

**大模型是"增强项"而不是"必需项"。** 意图识别走双通道：有 API Key 就用大模型做语义理解，
没有或调用失败自动回退到内置规则解析器。两个通道的结果会合并，规则通道负责补全金额、
日期这类硬信息（正则比大模型更可靠）。

**风控规则只有一份。** 限额、二次确认、身份校验、异常交易识别的判定全部集中在
`finagent/risk/engine.py`，账单分析工具和转账工具都复用它，不会出现两套规则互相打架。

## 三、快速开始

### 环境要求

- Python 3.9 及以上（实测 3.13）
- 无需安装任何第三方依赖

### 安装与启动

```bash
cd ai_banking_agent
python run.py
```

Windows 用户也可以直接**双击项目目录下的 `start.cmd`**，
会自动切到 UTF-8 编码、进入本目录并启动对话，不需要敲任何命令。

### H5 / APP / IM 接口

启动 HTTP 服务和 H5 聊天页面：

```powershell
python run_api.py --host 0.0.0.0 --port 8000
```

Windows 也可以直接双击 `start_web.cmd`。电脑访问：

```text
http://127.0.0.1:8000
```

同一 Wi-Fi 下的手机使用终端显示的局域网地址，例如：

```text
http://192.168.1.25:8000
```

H5 支持点击回形针上传账单图片/文本、全页面拖拽上传和剪贴板粘贴图片。
上传后会先进入 OCR 核对页，不会直接导入流水。
若设置了 `FINAGENT_WEB_PASSWORD`，网页首次请求会自动弹出口令输入框。

当前提供以下接口：

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/v1/sessions` | 创建会话 |
| `POST` | `/v1/messages` | 发送消息并返回完整回复 |
| `POST` | `/v1/messages/stream` | 发送消息并通过 SSE 返回 |
| `POST` | `/v1/uploads` | 上传账单图片/TXT/CSV 并进入核对页 |
| `POST` | `/v1/channels/wecom/events` | 企业微信网关事件适配入口 |
| `GET` | `/health` | 服务健康检查 |

`request_id` 用于请求幂等，同一会话重复提交不会重复转账或申购。
企业微信网关适配入口接收 JSON，并通过 `X-FinAgent-Signature`
和 `FINAGENT_WEBHOOK_SECRET` 做 HMAC-SHA256 校验。
所有涉及资金、卡片、持仓、订阅和绑卡的操作，会先显示关键信息核对页；
生日惊喜场景还会强制要求用户输入生日，不能直接使用画像中的默认日期。

> 本项目只是桌面上的一个普通文件夹，不会安装进你的 Python 环境，
> 也不会往 `site-packages` 写任何东西。删掉文件夹即可彻底移除。

看到提示符后直接输入中文即可：

```
用户> 给老婆转2000块，备注生日礼物，用微信
Agent> 转账成功（微信）：2,000.00 元已转给「林雅雯」
       付款账户：活期账户（尾号 6222）  可用余额 30,860.52 元
       流水号：TXN000613
       备注：生日礼物
       工具调用：
         [OK ] transfer.send(payee='老婆', amount=2000.0, channel='wechat', note='生日礼物')
```

### 输入方式说明（整段粘贴怎么用）

支持三种输入方式，**都不需要靠"多按一次回车"来结束**：

**1）逐行输入** —— 敲一句话按回车，Agent 立刻响应。和以前完全一样。

**2）整段粘贴** —— 直接把微信/支付宝账单粘进来，粘完按一次回车（或等约 0.5 秒）。
程序靠两个信号判断"这一段粘完了"：

- **完整性判断**：如果这一行"看起来不像一条完整指令"（行尾是金额、或整行只是个时间戳），
  就认为后面还有内容，继续收；
- **静默窗口**：0.5 秒内没有新内容，就认为这段粘贴结束。

遇到 `/命令`、或"确认/取消"这类完整指令会立刻停下并把它留给下一轮，
所以粘贴完接着输入"确认"不会被吞进账单里。

> 这套判断不依赖终端类型。之前用 `msvcrt.kbhit()` 探测控制台缓冲区，
> 只在真正的 conhost 里有效，stdin 被包装成管道时（某些嵌入式终端面板）就会失效，
> 又退化成逐行激活。现在换成后台线程读 stdin + 静默窗口，三种终端表现一致。

**3）模板文件导入（最稳，推荐演示用）** —— 把账单存成 txt，然后：

```
/import samples/bill_template.txt
```

`samples/bill_template.txt` 就是一个可直接编辑的模板：把「可直接编辑区」的三行
换成你自己的账单即可，`#` 开头的注释行会被自动忽略。
这种方式完全不经过终端粘贴，任何环境都不会翻车。

## 六、架构说明

### 分层与职责

| 层 | 模块 | 职责 | 不负责什么 |
|----|------|------|-----------|
| 渠道层 | `api/`、`web/`、`run_api.py` | HTTP、SSE、H5、IM 会话与幂等 | 不包含业务判断 |
| 交互层 | `cli/app.py`、`run.py` | 输入输出、命令、时间快进 | 不包含任何业务判断 |
| 理解层 | `nlu/` | 一句话 -> 结构化意图 + 槽位 | 不决定做什么业务动作 |
| 识别层 | `vision/` | 账单截图 -> 结构化交易（多模态 / 系统 OCR） | 不写库、不判断异常 |
| 编排层 | `agent/` | 补槽、规划、状态管理、调度 | 不实现具体业务逻辑 |
| 风控层 | `risk/engine.py`、`risk/scorecard.py` | 限额、确认、验证、异常识别、风险测评评分卡 | 不直接改数据 |
| 工具层 | `tools/` | 一个工具只做一件事 | 不做风控判断 |
| 数据层 | `data/` | 模型、统一提供接口、沙箱适配器、行情、SQLite 持久化、时钟 | 不含业务规则 |

### 一次请求的完整链路

以「给老婆转2000块，备注生日礼物，用微信」为例：

1. `IntentParser` 解析出 `transfer.send`，槽位 `{payee: 老婆, amount: 2000, channel: wechat, note: 生日礼物}`；
2. `Planner` 查注册表，发现 `transfer.send` 的必填参数都齐了，生成单步计划；
3. `Planner._describe_step` 解析收款人、收款渠道和付款账户，生成关键信息核对页；
4. 用户确认收款人、渠道、付款账户和金额后，进入风控校验；
5. `TransferTool.run` 扣款、记流水、更新收款人常用列表；
6. `AgentReply` 返回话术 + 结构化数据 + 工具调用轨迹。

如果金额是 25000 元，则第 4 步会返回 `requires_confirmation + requires_verification`，
对话状态机先要求回复"确认"，再要求输入短信验证码，两次都通过才执行。

### 多步规划示例

有些意图天然需要串多个工具，规划器会生成真正的多步计划：

| 意图 | 计划 | 说明 |
|------|------|------|
| `crossscene.birthday_plan` | `goal.create` -> `crossscene.schedule_gift(鲜花)` -> `crossscene.schedule_gift(蛋糕)` | 先锁定资金，再在生日前 2 天预约两次下单 |
| `card.report_lost` | `card.freeze` -> `card.report_lost` | 先冻结止损，再挂失补卡 |

多步计划只做**一次**二次确认，确认文案会把三步都列清楚。

### 三级识别策略（自动降级）

除了图片，**直接把账单文本粘贴进来**也能识别。微信/支付宝导出的账单
常见排版是"商户+金额一行、时间在下一行"，解析器会把相邻两行配对成一条记录：

```
用户> 抖音电商商家   -148.72
      10月14日13:11
      微信红包-发给何心熠   -2.50
      10月14日08:47
      转账-退款   +6.50
      10月14日08:45
Agent> 已识别「粘贴的账单文本」中的 3 笔交易（识别方式：粘贴文本解析）：
         日期        时间   商户                 金额     类别
         2026-10-14  13:11  抖音电商商家         -148.72  其他
         2026-10-14  08:47  微信红包 发给何心熠  -2.50    人情往来
         2026-10-14  08:45  转账 退款            6.50     转账
       请回复「确认」继续执行，或「取消」放弃。
```

注意"转账-退款 +6.50"这类行**不会**被当成转账指令——整段粘贴会被识别为账单，
整体交给解析器，而不是逐行去做意图识别。

### 最稳的方式：模板文件导入

如果所在终端粘贴表现不稳定，直接走文件，完全不经过终端粘贴：

1. 复制 `samples/bill_template.txt` 到你自己的目录；
2. 把「可直接编辑区」的三行示例换成你的账单内容（`#` 开头的行会被忽略）；
3. 保存为 UTF-8 的 `.txt`；
4. 在 Agent 里执行 `/import C:\你的路径\my_bill.txt`。

也可以一直用自带的模板演示：`/import samples/bill_template.txt`。

| 后端 | 依赖 | 能否离线 | 适用场景 |
|------|------|---------|---------|
| 多模态大模型 | 配置 API Key + 视觉模型 | 否 | 真实手机截图、版式复杂、需要语义归一化 |
| **Windows 内置 OCR** | 无（Windows 10/11 自带） | **是** | 现场答辩无网络、票据拍照 |
| 文本账单解析 | 无 | 是 | 银行导出的 CSV / TXT 账单 |

配置了 API Key 就优先用多模态模型，否则自动切到 Windows OCR；
两条路都不可用时给出明确的排查指引，不会静默失败。

### 实现要点

- `finagent/vision/win_ocr.ps1` 通过 `Windows.Media.Ocr` 调用系统 OCR 引擎。
  注意 WinRT 类型投影只在 **Windows PowerShell 5.1** 里可用（PowerShell 7 已移除该能力），
  所以代码显式调用 `powershell.exe` 而不是 `pwsh`；识别结果写入 UTF-8 临时文件，
  绕开终端代码页导致的乱码。
- `finagent/vision/receipt_parser.py` 专门做 OCR 后处理。真实 OCR 输出很脏，
  这里处理了五类典型噪声：中文之间插空格（`携 程 旅 行 网`）、
  连字符被识别成汉字（`2026 一 10 一 12`）、全角标点、
  小数点被吞（`2480 00` → `2480.00`）、以及某些引擎"按列重排"
  （先输出所有日期再输出金额）。行解析失败时自动退化为"按列顺序对齐"。
- 识别结果**不直接入库**：先让用户核对，回复「确认」才写入流水。
  重复扫描同一张图会自动去重，且导入的记录不影响账户余额（属于账单补录而非资金变动）。

## 九、风控设计

### 1. 转账限额

| 规则 | 阈值 | 位置 |
|------|------|------|
| 单笔上限 | 50,000 元 | `RiskPolicy.SINGLE_TRANSFER_LIMIT` |
| 单日累计上限 | 200,000 元 | `RiskPolicy.DAILY_TRANSFER_LIMIT` |
| 新收款人单笔上限 | 5,000 元 | `RiskPolicy.NEW_PAYEE_LIMIT` |
| 二次确认（新收款人） | 1,000 元 | `RiskPolicy.CONFIRM_THRESHOLD` |
| 二次确认（常用收款人） | 5,000 元 | `RiskPolicy.TRUSTED_CONFIRM_THRESHOLD` |
| 短信身份验证 | 20,000 元 | `RiskPolicy.VERIFY_THRESHOLD` |

行为特征也会参与判断：00:00-05:00 夜间大额转账、10 分钟内连续多笔转出，
都会提升风险等级并要求人工确认。

### 2. 二次确认与身份验证

高风险工具（挂失、冻结、申购、赎回、取消订阅）无论金额大小都需要二次确认；
超过 20,000 元的资金操作在确认之后还要输入短信验证码（演示环境固定 `123456`）。
连续输错 3 次自动终止，并提示"如非本人操作请立即修改密码并冻结卡片"。

### 3. 异常交易识别（账单分析场景）

规则只有一份，账单工具、每日简报、定时巡检都调用同一个引擎：

| 类型 | 判定逻辑 | 等级 |
|------|---------|------|
| `night_large` | 00:00-05:00 且金额 >= 1000 元 | 高危 |
| `duplicate_charge` | 同商户同金额在 10 分钟内被扣 2 次以上 | 关注 |
| `amount_outlier` | 金额 > 同类别均值 + 3 倍标准差，且 > 均值 3 倍 | 关注 |
| `subscription_hike` | 订阅月费较历史涨价超过 20% | 关注 |
| `micro_burst` | 1 小时内出现 4 笔以上 20 元以下小额扣款 | 关注 |
| `new_merchant_large` | 首次在陌生商户消费且金额 >= 5000 元 | 关注 |
| `overseas` | 境外商户消费 | 提示 |

命中"高危"时还会自动写入提醒（`store.alerts`），体现主动风控。
异常结果同时带有 0-100 风险分和量化指标，例如金额离群会输出
`zscore / category_mean / threshold`，深夜大额会输出命中小时，
便于答辩时解释"为什么判为异常"。可运行：

```powershell
python scripts\demo_anomaly_case.py
```

### 4. 风险测评：可解释评分卡，不是黑盒模型

"风险测评要不要建模？"——需要模型，但**不需要训练模型**。

监管口径下的投资者风险承受能力评估，本质是规则化的评分卡：
若干维度加权打分，再按阈值映射到 R1-R5。它要求可解释、可复现、可审计，
恰恰不适合黑盒。真正需要训练模型的是产品推荐排序、流失预测、反欺诈评分，
本项目用规则 + 统计实现，反而更容易向评委讲清楚。

`finagent/risk/scorecard.py` 里的评分卡：5 个维度、10 个打分项、总分 100。

| 维度 | 分值 | 打分项 |
|------|------|--------|
| 财务状况 | 30 | 收入水平、资产厚度（金融资产/月支出）、应急金覆盖月数、信用卡负债率 |
| 投资经验 | 15 | 持有产品数、投资年限、资产分散度 |
| 风险态度 | 25 | 客户登记风险偏好 |
| 投资期限 | 15 | 年龄与规划期 |
| 流动性需求 | 15 | 活期资金占比 |

阈值映射：`≥90 → R5`、`≥76 → R4`、`≥55 → R3`、`≥40 → R2`、其余 R1。
每个打分项都会输出"得了多少分、为什么"，可以直接展示给客户或用于合规审查。

另外附带**回撤压力测试**：按当前金融资产测算市场下跌时的浮亏，
与客户可承受的最大回撤（R1 5% / R2 10% / R3 20% / R4 30% / R5 40%）做对比。

实测（演示客户陈晓明）：总分 **70/100 → R3 平衡型**，
其中财务状况 20/30、投资经验 10/15、风险态度 15/25、投资期限 12/15、流动性需求 13/15。

### 5. 投资者适当性管理

理财申购前先跑评分卡。产品风险等级高于客户承受能力两级以上时直接拦截，
并给出同等级的替代产品；高一级时允许购买但显著提示风险。
"能不能买"由评分卡统一裁决，推荐、申购、持仓复查三处口径一致。

**理财操作前必须先做问卷。** 任何「推荐 / 申购 / 风险测评」请求，都会先触发一份
“6 道计分题 + 1 道一致性校验题”的基础风险问卷。第 6 题改为投资目标，
活期覆盖月数改为降级触发器：不足 1 个月时无论总分多少最高只能评为 C2。
问卷没完成前不会调用任何推荐或交易工具：

```
用户> 给我推荐几个基金
Agent> 开始推荐前，先完成 6 道计分题和 1 道一致性校验题。
       这是投资者适当性管理的要求：没有评估风险承受能力，不能推荐或销售理财产品。
       第 1/7 题：您的年收入大约是多少？
         为什么问：这题决定您的现金流稳定性和可承受的投资金额。
         A. 10 万以下   B. 10-30 万   C. 30-100 万   D. 100 万以上
用户> b
...
Agent> 评估完成：C3 平衡型（65/100）。
       可买产品：R1-R3；R4 需签风险不匹配警示书并二次确认；R5 及以上禁止销售。
```

支持回复字母、序号或选项原文；回复「跳过」时先展示推断值、依据和置信度，
用户确认后才采用并记录确认时间；回复「取消」中止。
问卷结果写入会话，后续推荐按实测 C 级执行，`/reset` 会清空重来。
第 5 题使用反向选项；第 7 题与亏损容忍交叉校验，不一致时取较低等级。
活期资金不足 1 个月时会强制封顶 C2。C1 客户购买 R2 产品必须记录风险不匹配警示，
进入 24 小时冷静期，结束后才能再次确认申购。

## 十三、扩展指南

### 新增一个业务工具（三步）

1. 写一个 `Tool` 子类（建议按业务域放到对应的 `tools/*.py`）：

```python
class ExchangeRateTool(Tool):
    name = "forex.rate"
    category = "跨境服务"
    description = "查询汇率并试算换汇金额"
    params = [
        ToolParam("currency", "string", True, "外币代码，如 USD"),
        ToolParam("amount", "number", False, "换汇金额（元）"),
    ]

    def run(self, ctx, currency, amount=None):
        ...
        return ToolResult(True, "...", data={...})
```

2. 在 `finagent/agent/registry.py` 的 `build_default_registry()` 里注册一行；
3. 在 `finagent/nlu/intent_schema.py` 加一条 `IntentSpec`，并在
   `finagent/agent/planner.py` 的 `SIMPLE_PLANS` 里加一条映射。

### 新增一个场景

- **多步场景**：在 `Planner` 里加一个 `_xxx_plan()` 方法，返回多个 `PlanStep` 即可，
  参考 `_birthday_plan()`。
- **调整风控**：只改 `config.py` 的 `RiskPolicy` 或 `risk/engine.py`，其它模块不用动。
- **调整风险测评**：改 `finagent/risk/scorecard.py` 里的打分项与阈值即可，
  评分卡是纯配置化的，新增一个维度不需要动推荐和适当性代码。
- **接入新的 OCR 引擎**：在 `finagent/vision/receipt_reader.py` 里加一个
  `_from_xxx()` 方法并挂进 `read()` 的优先级链，解析部分可以复用
  `receipt_parser.parse_receipt_text()`。
- **换数据源**：实现 `BankAdapter` 或替换 `build_data_providers()` 的 Provider，
  工具层仍然只消费统一接口；生产部署再替换公开行情源和 SQLite 投影。

## 十四、已知限制与后续规划

| 限制 | 说明 |
|------|------|
| 仍是原型事务边界 | SQLite 已保存会话、账户、持仓、任务和审计投影，但未实现生产级连接池、分布式锁和完整事务编排 |
| 验证码是固定值 | 演示环境固定 `123456` |
| 无真实对接 | 不接征信、支付通道、银行核心系统；目前使用可控的银行沙箱适配器 |
| 意图清单是白名单 | 规则与 LLM 都只认已登记的意图，超出范围会引导用户换个说法 |
| 订阅识别是启发式 | 基于金额稳定性与扣费间隔，不是商户协议数据库 |
| OCR 有误差 | Windows 离线 OCR 对清晰截图识别率尚可，但版式复杂的真实截图建议走多模态模型；识别结果一律先让用户核对再入库 |
| 风险测评为内置评分卡 | 不是监管要求的完整问卷，也不含问卷答案校验、录音录像等流程 |

后续可以做的方向：接入真实风险测评问卷、把意图识别换成 function calling、
加多用户会话隔离、把工具调用轨迹做成可视化面板。
