# AI Banking Agent · 智能银行代理系统

> 合并版 v4：六大核心业务、财务数字孪生、主动 CFO、风险处置链、多 Agent 工作流、
> LLM Tool Calling、OCR 质量审计、透明理财风险分析和可重复评测的完整集合。

> 2026 FinTechathon 深圳国际金融科技大赛（微众银行金融科技大学生挑战赛）· 人工智能国内赛道
>
> 赛题：构建 AI Banking Agent 智能银行代理系统
>
> **本系统为赛事原型 Demo：所有账户、交易、理财与卡片数据均为模拟数据，不接入任何真实银行系统、征信或资金接口，不可用于真实银行业务。**

## 一、项目简介

用自然语言对话完成银行日常业务：转账、看账单、买理财、管卡片、管订阅，
以及跨场景的主动服务（识别重要日期并自动安排）。

技术上不是"把 LLM 接上几个函数"的演示，而是一套完整的分层 Agent 架构：

```
自然语言
  -> 意图识别（大模型优先 / 规则兜底）
  -> 槽位补全（多轮对话追问）
  -> 任务规划（单步 or 跨工具多步计划）
  -> 风控校验（限额 / 二次确认 / 身份验证 / 拦截）
  -> 工作流与 Agent 角色编排（理解 / 风控 / 顾问 / 执行）
  -> 工具执行（52 个银行业务与智能财务工具）
  -> 自然语言应答 + 工具调用轨迹
```

### 三个技术取舍

**不依赖任何第三方库也能跑。** 全部用 Python 标准库实现（HTTP 调用用 `urllib`），
`python run.py` 直接启动，断网也能完整演示六大场景。这样答辩现场不会因为装包失败翻车。

**大模型是"增强项"而不是"必需项"。** 意图识别走双通道：有 API Key 就用大模型做语义理解，
没有或调用失败自动回退到内置规则解析器。两个通道的结果会合并，规则通道负责补全金额、
日期这类硬信息（正则比大模型更可靠）。

**风控规则只有一份。** 限额、二次确认、身份校验、异常交易识别的判定全部集中在
`finagent/risk/engine.py`，账单分析工具和转账工具都复用它，不会出现两套规则互相打架。

## 二、六大核心场景

| # | 场景 | 覆盖能力 | 典型说法 |
|---|------|---------|---------|

| 4 | 卡片管理 | 卡申请、额度调整、交易限制/解锁、挂失 | 我有哪些卡 / 信用卡额度提到3万 / 关闭信用卡的境外交易 / 我的卡丢了帮我挂失 |

额外拓展：账户总览、客户画像、消费关键词检索、每日主动简报、
定时任务执行器（`/advance` 快进时间）、投资者适当性管理、审计日志、
**账单/小票截图 OCR 识别**、**可解释的风险测评评分卡**。

### 高级 Agent 能力（v4）

| 能力 | 说明 | 示例 |
|---|---|---|
| 财务数字孪生 | 预测未来 30/60/90 天现金流、最低余额和资金缺口 | 预测我未来90天的现金流 |
| 情景试算 | 计算大额消费、收入变化或新增月支出对余额的影响 | 如果下个月买8000元电脑会怎样 |

| 风险事件处置链 | 生成止损、核对、争议、补卡、持续监控五步方案 | 给我最近异常交易的风险处置方案 |
| 账务对账 | 检查银行卡、关联账户与总资产是否一致，并支持确认式人工修正 | 帮我做账务对账 |
| 专业理财分析 | 透明估算波动率、最大回撤、费率拖累与相关性 | 分析这些理财产品的风险 |
| AA 收款进度 | 查看参与人状态并生成模拟分享文案 | AA收款进度 |
| 财务健康分 | 7 维度分段基准评分、参考标准和分步改善建议 | 我的财务健康分 |
| 主动事件中心 | 现金流、账单、订阅和风险事件统一提醒，统计/优先级/稍后/忽略状态持久化 | 我的主动事件 |
| 卡片生命周期 | 申请、审批、激活、拒绝时间线和一次性虚拟卡信息 | 查看信用卡申请进度 |
| 信用卡账单 | 账单日、还款日、最低还款、利息、费用和临时额度 | 查看信用卡账单 |

每次回复还会附带工作流元数据：`workflow_id`、当前状态、参与的 Agent 角色和工具步骤。
多步待确认任务会沿用同一个工作流编号。

转账与还款流水包含生命周期状态、银行处理流水号、提交/完成时间、预计到账时间和风控依据。
页面可以直接打开交易凭证。首次向新收款人进行较大金额转账会进入 10 分钟安全冷静期；
大额操作的验证码包含有效期、错误次数和重新发送机制。

## 三、快速开始

### 环境要求

- Python 3.9 及以上（实测 3.13）
- 无需安装任何第三方依赖

### 安装与启动

```bash
cd ai_banking_agent
python run.py
```

Windows 用户也可以直接**双击项目目录下的 `start.cmd`**，
会自动切到 UTF-8 编码、进入本目录并启动对话，不需要敲任何命令。

### H5 / APP / IM 接口

启动 HTTP 服务和 H5 聊天页面：

```powershell
python run_api.py --host 0.0.0.0 --port 8000
```

Windows 也可以直接双击 `start_web.cmd`。电脑访问：

```text
http://127.0.0.1:8000
```

同一 Wi-Fi 下的手机使用终端显示的局域网地址，例如：

```text
http://192.168.1.25:8000
```

H5 支持点击回形针上传账单图片/文本、全页面拖拽上传和剪贴板粘贴图片。
上传后会先进入 OCR 核对页，不会直接导入流水。
若设置了 `FINAGENT_WEB_PASSWORD`，网页首次请求会自动弹出口令输入框。

当前提供以下接口：

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/v1/sessions` | 创建会话 |
| `POST` | `/v1/messages` | 发送消息并返回完整回复 |
| `POST` | `/v1/messages/stream` | 发送消息并通过 SSE 返回 |
| `POST` | `/v1/uploads` | 上传账单图片/TXT/CSV/XLSX/XLSM 并进入核对页 |
| `GET` | `/v1/uploads?session_id=...` | 查看当前会话的上传批次 |
| `DELETE` | `/v1/uploads/{batch_id}?session_id=...` | 删除指定批次及其导入流水 |
| `GET` | `/v1/profile?session_id=...` | 查看个人资料、关心的人和银行卡 |
| `PATCH` | `/v1/profile` | 修改个人资料与关心的人 |
| `POST` | `/v1/cards` | 添加演示银行卡 |
| `PATCH` | `/v1/cards/{card_id}` | 修改演示银行卡设置 |
| `DELETE` | `/v1/cards/{card_id}?session_id=...` | 删除当前会话的演示银行卡 |
| `POST` | `/v1/channels/wecom/events` | 企业微信网关事件适配入口 |
| `GET` | `/v1/transactions/{txn_id}` | 交易生命周期与交易凭证 |
| `POST` | `/v1/forecast/simulate` | 交互式现金流情景测算 |
| `GET` | `/v1/events` | 主动财务事件中心 |
| `POST` | `/v1/events/action` | 处理、稍后提醒或忽略事件 |
| `GET/PATCH` | `/v1/receipts/pending` | 获取和校正待导入账单 |
| `GET` | `/health` | 服务健康检查 |

`request_id` 用于请求幂等，同一会话重复提交不会重复转账或申购。
企业微信网关适配入口接收 JSON，并通过 `X-FinAgent-Signature`
和 `FINAGENT_WEBHOOK_SECRET` 做 HMAC-SHA256 校验。
所有涉及资金、卡片、持仓、订阅和绑卡的操作，会先显示关键信息核对页；
生日惊喜场景还会强制要求用户输入生日，不能直接使用画像中的默认日期。

## 四、LLM Tool Calling 与离线回退

默认开启受控的 LLM Tool Calling：

1. 模型只能从当前意图允许的工具中选择；
2. 模型不能创造工具名；
3. 已由规则抽取的金额、日期、卡片和账户参数优先级最高；
4. 风控、二次确认和身份认证仍由本地确定性代码执行。

如果模型、接口或参数校验失败，会自动回退到原有确定性 Planner。可通过环境变量关闭：

```powershell
$env:FINAGENT_LLM_TOOL_CALLING="false"
```

H5 侧边栏提供“资料与卡片设置”，并明确标注当前资料来自预设演示数据。
可修改姓名、手机号、城市、年龄、职业、月收入、用户自己的生日，以及“关心的人”列表。
每个人支持姓名、关系、生日、纪念日、偏好礼物和避讳，可随时增加或删除；
资金目标支持新增、修改和删除，新增目标不会自动锁定资金，删除时会释放关联账户中的锁定资金；
银行卡额度和状态也可修改，全部写入当前会话 SQLite。

绑卡使用分步校验：银行卡号需为 16–19 位、符合银联储蓄卡常见 `62` 开头规则并通过
Luhn 校验；系统还会检查 BIN 前缀与所选发卡行是否一致。预留手机号必须为
`13`–`19` 开头的 11 位数字。演示 BIN 库只覆盖常见样本，不是银行全量 BIN 数据。

“绑卡”和“开卡”使用不同流程。绑卡需要已有卡的卡号、密码和预留手机号；
储蓄卡开户会收集手机号、I/II 类账户和开户城市，并要求两次输入 6 位取款密码；
系统会检查两次输入是否一致，并评估连续数字、重复模式和常见弱密码风险，明文密码不写入历史或调用轨迹；
信用卡申请还会收集就业、收入、负债、期望额度和用途，必须选择“已上传流水”或“演示流水”，
并确认模拟评估授权。流水核验会统计覆盖月份、笔数、月均支出、主要类别和异常特征，
随后即时返回模拟预审结果，并展示 1–3 个工作日的模拟终审时限。整个流程不会查询征信。

银行卡采用统一账务口径：每张借记卡/虚拟卡绑定一个账户，卡列表直接显示余额和可用金额，
每次转账或还款都会同步更新交易流水、卡余额和关联账户余额。查询“总资产”时按所有有效
借记卡/虚拟卡余额求和，信用卡已用额度作为负债单独展示，不计入资产。

转账认证模拟真实流程：先核对收款人、金额和付款卡，再输入付款卡 6 位交易密码；
达到大额阈值后继续输入短信验证码。演示种子卡的交易密码为 `246810`，新开卡使用开户时
设置的密码，密码只保存哈希并存为敏感字段，不进入对话历史和工具调用轨迹。

- 本人卡互转：`从工资卡转1000到定期卡`，两张卡余额同时变化，总资产保持不变。
- 信用卡还款：`用工资卡还信用卡3000元`，借记卡余额减少、信用卡已用额度同步减少。
- 外部转账：`从工资卡给王强转500元，用微信`，完成确认、交易密码及必要的短信验证后入账。

通过账单截图/CSV 导入的外部流水仍进入“上传账单余额”虚拟账户，不冒充某张真实银行卡的扣款，
避免把外部历史账单重复扣减到当前卡片余额。

> 本项目只是桌面上的一个普通文件夹，不会安装进你的 Python 环境，
> 也不会往 `site-packages` 写任何东西。删掉文件夹即可彻底移除。

### 输入方式说明（整段粘贴怎么用）

支持三种输入方式，**都不需要靠"多按一次回车"来结束**：

**1）逐行输入** —— 敲一句话按回车，Agent 立刻响应。和以前完全一样。

**2）整段粘贴** —— 直接把微信/支付宝账单粘进来，粘完按一次回车（或等约 0.5 秒）。
程序靠两个信号判断"这一段粘完了"：

- **完整性判断**：如果这一行"看起来不像一条完整指令"（行尾是金额、或整行只是个时间戳），
  就认为后面还有内容，继续收；
- **静默窗口**：0.5 秒内没有新内容，就认为这段粘贴结束。

遇到 `/命令`、或"确认/取消"这类完整指令会立刻停下并把它留给下一轮，
所以粘贴完接着输入"确认"不会被吞进账单里。

> 这套判断不依赖终端类型。之前用 `msvcrt.kbhit()` 探测控制台缓冲区，
> 只在真正的 conhost 里有效，stdin 被包装成管道时（某些嵌入式终端面板）就会失效，
> 又退化成逐行激活。现在换成后台线程读 stdin + 静默窗口，三种终端表现一致。

**3）模板文件导入（最稳，推荐演示用）** —— 把账单存成 txt，然后：

```
/import samples/bill_template.txt
```

`samples/bill_template.txt` 就是一个可直接编辑的模板：把「可直接编辑区」的三行
换成你自己的账单即可，`#` 开头的注释行会被自动忽略。
这种方式完全不经过终端粘贴，任何环境都不会翻车。

# Windows PowerShell
$env:FINAGENT_LLM_API_KEY="sk-xxxx"
$env:FINAGENT_LLM_BASE_URL="https://api.deepseek.com/v1"

### 一次请求的完整链路

以「给老婆转2000块，备注生日礼物，用微信」为例：

1. `IntentParser` 解析出 `transfer.send`，槽位 `{payee: 老婆, amount: 2000, channel: wechat, note: 生日礼物}`；
2. `Planner` 查注册表，发现 `transfer.send` 的必填参数都齐了，生成单步计划；
3. `Planner._describe_step` 解析收款人、收款渠道和付款账户，生成关键信息核对页；
4. 用户确认收款人、渠道、付款账户和金额后，进入风控校验；
5. `TransferTool.run` 扣款、记流水、更新收款人常用列表；
6. `AgentReply` 返回话术 + 结构化数据 + 工具调用轨迹。

如果金额是 25000 元，则第 4 步会返回 `requires_confirmation + requires_verification`，
对话状态机先要求回复"确认"，再要求输入短信验证码，两次都通过才执行。

### 多步规划示例

有些意图天然需要串多个工具，规划器会生成真正的多步计划：

| 意图 | 计划 | 说明 |
|------|------|------|
| `crossscene.birthday_plan` | `goal.create` -> `crossscene.schedule_gift(鲜花)` -> `crossscene.schedule_gift(蛋糕)` | 先锁定资金，再在生日前 2 天预约两次下单 |
| `card.report_lost` | `card.freeze` -> `card.report_lost` | 先冻结止损，再挂失补卡 |

多步计划只做**一次**二次确认，确认文案会把三步都列清楚。

## 九、账单截图识别

账单分析不只能读结构化流水，也能直接读**账单截图 / 小票照片 / Excel 文件**。
Excel 支持 `.xlsx` 和 `.xlsm`，使用 Python 标准库解析，不要求额外安装 `openpyxl`。
旧式二进制 `.xls` 请先另存为 `.xlsx`。

```
用户> 识别这张账单截图 samples/bill_sample.png
Agent> 已识别「bill_sample.png」中的 6 笔交易（识别方式：Windows 内置 OCR（离线））：
         日期        时间   商户        金额       类别
         ----------  -----  ----------  ---------  ----
         2026-10-12  10:05  携程旅行网  -2,480.00  旅行
         2026-10-12  10:06  携程旅行网  -2,480.00  旅行
         2026-10-12  18:30  星巴克咖啡  -38.00     餐饮
         2026-10-13  09:10  滴滴出行    -42.50     交通
         2026-10-13  20:00  京东商城    -899.00    购物
         2026-10-14  08:15  瑞幸咖啡    -19.90     餐饮
         合计支出 5,959.40 元（6 笔支出）

       请回复「确认」继续执行，或「取消」放弃。

用户> 确认
Agent> 已导入 6 笔流水（识别来源：Windows 内置 OCR（离线））。
         说明：导入的是账单明细补录，不会重复扣减账户余额。
       导入后立即发现 1 笔异常交易：
         「携程旅行网」在 10 分钟内被扣款 2 次，每笔 2,480.00 元，疑似重复扣款
```

如果上传的是**账单汇总页**，系统不会把“合计”误导入成流水，而会提取本月总支出、
消费构成和过去几个月的支出趋势，直接给出分析。例如：

```text
已识别账单汇总页（2026-10）
  本月支出 7,283.34 元

消费构成：
  购物 2,400.00  33.0%
  娱乐 1,683.34  23.0%
  ...

过去月份对比：
  2026-07  5,800.00  -
  2026-08  6,200.00  +6.9%
  ...
```

可直接使用 `samples/bill_summary_sample.png` 体验该流程。

Excel 账单可以放逐笔交易列（日期/商户/金额/类别），也可以放汇总表
（月份/支出、类别/金额/占比）；两种表都会自动识别。
TXT/CSV 会自动识别 UTF-8、带 BOM 的 UTF-8、GBK/GB18030 和 UTF-16 编码。
导入成功后，账单分析、异常检测、月报和搜索会自动切换为“仅用户上传流水”，
不会再把模拟种子流水混入真实数据；没有上传流水时才使用演示数据兜底。
H5 侧边栏的“查看上传记录”可以检查批次文件名、导入时间、交易笔数和支出，
也可以整批删除。原始上传文件在识别后立即删除，解析后的流水和批次元数据
保存在当前会话的 SQLite 快照中，删除批次后会同步清理。

多模态识别会要求模型返回 `date / merchant / amount / category` 的字段级置信度；
Windows OCR 也会按字段完整度生成可解释置信度。核对表中的低置信度单项会单独标红，
人工修改后可通过 PATCH `/v1/receipts/pending` 重新执行质量与金额守恒校验。
超过 4096 像素的截图会在 Windows OCR 前自动等比降采样，避免引擎因尺寸过大直接失败。

### 三级识别策略（自动降级）

除了图片，**直接把账单文本粘贴进来**也能识别。微信/支付宝导出的账单
常见排版是"商户+金额一行、时间在下一行"，解析器会把相邻两行配对成一条记录：

```
用户> 抖音电商商家   -148.72
      10月14日13:11
      微信红包-发给何心熠   -2.50
      10月14日08:47
      转账-退款   +6.50
      10月14日08:45
Agent> 已识别「粘贴的账单文本」中的 3 笔交易（识别方式：粘贴文本解析）：
         日期        时间   商户                 金额     类别
         2026-10-14  13:11  抖音电商商家         -148.72  其他
         2026-10-14  08:47  微信红包 发给何心熠  -2.50    人情往来
         2026-10-14  08:45  转账 退款            6.50     转账
       请回复「确认」继续执行，或「取消」放弃。
```

注意"转账-退款 +6.50"这类行**不会**被当成转账指令——整段粘贴会被识别为账单，
整体交给解析器，而不是逐行去做意图识别。

### 最稳的方式：模板文件导入

如果所在终端粘贴表现不稳定，直接走文件，完全不经过终端粘贴：

1. 复制 `samples/bill_template.txt` 到你自己的目录；
2. 把「可直接编辑区」的三行示例换成你的账单内容（`#` 开头的行会被忽略）；
3. 保存为 UTF-8 的 `.txt`；
4. 在 Agent 里执行 `/import C:\你的路径\my_bill.txt`。

也可以一直用自带的模板演示：`/import samples/bill_template.txt`。

| 后端 | 依赖 | 能否离线 | 适用场景 |
|------|------|---------|---------|
| 多模态大模型 | 配置 API Key + 视觉模型 | 否 | 真实手机截图、版式复杂、需要语义归一化 |
| **Windows 内置 OCR** | 无（Windows 10/11 自带） | **是** | 现场答辩无网络、票据拍照 |
| 文本账单解析 | 无 | 是 | 银行导出的 CSV / TXT 账单 |

配置了 API Key 就优先用多模态模型，否则自动切到 Windows OCR；
两条路都不可用时给出明确的排查指引，不会静默失败。

### 实现要点

- `finagent/vision/win_ocr.ps1` 通过 `Windows.Media.Ocr` 调用系统 OCR 引擎。
  注意 WinRT 类型投影只在 **Windows PowerShell 5.1** 里可用（PowerShell 7 已移除该能力），
  所以代码显式调用 `powershell.exe` 而不是 `pwsh`；识别结果写入 UTF-8 临时文件，
  绕开终端代码页导致的乱码。
- `finagent/vision/receipt_parser.py` 专门做 OCR 后处理。真实 OCR 输出很脏，
  这里处理了五类典型噪声：中文之间插空格（`携 程 旅 行 网`）、
  连字符被识别成汉字（`2026 一 10 一 12`）、全角标点、
  小数点被吞（`2480 00` → `2480.00`）、以及某些引擎"按列重排"
  （先输出所有日期再输出金额）。行解析失败时自动退化为"按列顺序对齐"。
- 识别结果**不直接入库**：先让用户核对，回复「确认」才写入流水。
  重复扫描同一张图会自动去重，且导入的记录不影响账户余额（属于账单补录而非资金变动）。

| 二次确认（常用收款人） | 5,000 元 | `RiskPolicy.TRUSTED_CONFIRM_THRESHOLD` |
| 短信身份验证 | 20,000 元 | `RiskPolicy.VERIFY_THRESHOLD` |

行为特征也会参与判断：00:00-05:00 夜间大额转账、10 分钟内连续多笔转出，
都会提升风险等级并要求人工确认。

### 2. 二次确认与身份验证

高风险工具（挂失、冻结、申购、赎回、取消订阅）无论金额大小都需要二次确认；
超过 20,000 元的资金操作在确认之后还要输入短信验证码（演示环境固定 `123456`）。
连续输错 3 次自动终止，并提示"如非本人操作请立即修改密码并冻结卡片"。

### 3. 异常交易识别（账单分析场景）

规则只有一份，账单工具、每日简报、定时巡检都调用同一个引擎：

| 类型 | 判定逻辑 | 等级 |
|------|---------|------|
| `night_large` | 00:00-05:00 且金额 >= 1000 元 | 高危 |
| `duplicate_charge` | 同商户同金额在 10 分钟内被扣 2 次以上 | 关注 |
| `amount_outlier` | 金额 > 同类别均值 + 3 倍标准差，且 > 均值 3 倍 | 关注 |
| `subscription_hike` | 订阅月费较历史涨价超过 20% | 关注 |
| `micro_burst` | 1 小时内出现 4 笔以上 20 元以下小额扣款 | 关注 |
| `new_merchant_large` | 首次在陌生商户消费且金额 >= 5000 元 | 关注 |
| `overseas` | 境外商户消费 | 提示 |

命中"高危"时还会自动写入提醒（`store.alerts`），体现主动风控。
异常结果同时带有 0-100 风险分和量化指标，例如金额离群会输出
`zscore / category_mean / threshold`，深夜大额会输出命中小时，
便于答辩时解释"为什么判为异常"。可运行：

```powershell
python scripts\demo_anomaly_case.py
```

### 4. 风险测评：可解释评分卡，不是黑盒模型

"风险测评要不要建模？"——需要模型，但**不需要训练模型**。

监管口径下的投资者风险承受能力评估，本质是规则化的评分卡：
若干维度加权打分，再按阈值映射到 R1-R5。它要求可解释、可复现、可审计，
恰恰不适合黑盒。真正需要训练模型的是产品推荐排序、流失预测、反欺诈评分，
本项目用规则 + 统计实现，反而更容易向评委讲清楚。

`finagent/risk/scorecard.py` 里的评分卡：5 个维度、10 个打分项、总分 100。

| 维度 | 分值 | 打分项 |
|------|------|--------|
| 财务状况 | 30 | 收入水平、资产厚度（金融资产/月支出）、应急金覆盖月数、信用卡负债率 |
| 投资经验 | 15 | 持有产品数、投资年限、资产分散度 |
| 风险态度 | 25 | 客户登记风险偏好 |
| 投资期限 | 15 | 年龄与规划期 |
| 流动性需求 | 15 | 活期资金占比 |

阈值映射：`≥90 → R5`、`≥76 → R4`、`≥55 → R3`、`≥40 → R2`、其余 R1。
每个打分项都会输出"得了多少分、为什么"，可以直接展示给客户或用于合规审查。

另外附带**回撤压力测试**：按当前金融资产测算市场下跌时的浮亏，
与客户可承受的最大回撤（R1 5% / R2 10% / R3 20% / R4 30% / R5 40%）做对比。

实测（演示客户陈晓明）：总分 **70/100 → R3 平衡型**，
其中财务状况 20/30、投资经验 10/15、风险态度 15/25、投资期限 12/15、流动性需求 13/15。

### 5. 投资者适当性管理

理财申购前先跑评分卡。产品风险等级高于客户承受能力两级以上时直接拦截，
并给出同等级的替代产品；高一级时允许购买但显著提示风险。
"能不能买"由评分卡统一裁决，推荐、申购、持仓复查三处口径一致。

**理财操作前必须先做问卷。** 任何「推荐 / 申购 / 风险测评」请求，都会先触发一份
“6 道计分题 + 1 道一致性校验题”的基础风险问卷。第 6 题改为投资目标，
活期覆盖月数改为降级触发器：不足 1 个月时无论总分多少最高只能评为 C2。
问卷没完成前不会调用任何推荐或交易工具：

```
用户> 给我推荐几个基金
Agent> 开始推荐前，先完成 6 道计分题和 1 道一致性校验题。
       这是投资者适当性管理的要求：没有评估风险承受能力，不能推荐或销售理财产品。
       第 1/7 题：您的年收入大约是多少？
         为什么问：这题决定您的现金流稳定性和可承受的投资金额。
         A. 10 万以下   B. 10-30 万   C. 30-100 万   D. 100 万以上
用户> b
...
Agent> 评估完成：C3 平衡型（65/100）。
       可买产品：R1-R3；R4 需签风险不匹配警示书并二次确认；R5 及以上禁止销售。
```

支持回复字母、序号或选项原文；回复「跳过」时先展示推断值、依据和置信度，
用户确认后才采用并记录确认时间；回复「取消」中止。
问卷过程中如果发起查余额、账单、卡片等新指令，问卷会暂停而不是阻塞其他业务。
下次再次进入理财推荐时，Agent 会展示上次已选答案，并让用户选择
「继续上次记录」「重新开始」或「取消」。暂停状态会随 SQLite 会话持久化。
其他待补槽位、二次确认、短信验证和冷静期提示也不会锁住会话：
发送新的明确业务指令会取消当前未完成动作并立即处理新指令。
对上一项结果继续问「为什么」「为啥」「依据是什么」时，Agent 会结合最近的
工具轨迹和结构化数据解释判断依据；异常记录场景还会逐条说明命中的规则、量化指标
以及为什么给出对应建议。最近一次回复会随会话写入 SQLite。
问卷结果写入会话，后续推荐按实测 C 级执行，`/reset` 会清空重来。
第 5 题使用反向选项；第 7 题与亏损容忍交叉校验，不一致时取较低等级。
活期资金不足 1 个月时会强制封顶 C2。C1 客户购买 R2 产品必须记录风险不匹配警示，
进入 24 小时冷静期，结束后才能再次确认申购。

三条硬规矩：

1. 有行情的标「实时 / 净值」，没行情的标「演示」，**两类永远分开列表**，不混在一张表里；
2. 展示的是**当前价格与当日涨跌**，不把历史涨跌包装成"预期收益"；
3. 衍生品属于 R5、需要合格投资者认证，只做风险揭示、不给申购建议。

实时行情默认开启，断网或接口异常会自动降级为演示数据并明确提示。
想强制离线：`set FINAGENT_MARKET_MODE=off`（Windows）。

推荐结果会把实时行情产品和演示参数产品合并为一个**统一编号清单**，页面标题中的数量
严格等于实际展示条数，避免拆分表格造成“到底是几只”的歧义。每只产品都包含代码、类型、
风险等级、价格或收益参考、起投金额、流动性、数据来源，以及“它是什么、怎么赚钱、
适合谁、主要风险”的通俗说明。网页端使用产品卡片而不是长表格展示。

推荐会同时按两项条件筛选：风险适当性和实际支付能力。起投金额高于当前可动用银行卡余额的
产品不会出现在清单中；客户风险等级之上的相邻一级产品会标注“需确认”，更高风险产品不展示。
页面支持切换存款、债券、基金和“换一批”，推荐数量始终使用截断后的实际条数。
普通“基金”请求默认排除纯债基金；只有明确说“债券基金”时才进入债券基金池。
场内货币基金和ETF使用腾讯/东方财富公开行情，场外基金使用公开净值；取不到公开数据时
明确标记“公开行情未取回”，不会用演示收益冒充真实市场数据。

“产品推荐”和“产品对比”使用两个独立工具：

- 推荐负责筛选、适当性与预算约束、组合配置；
- 对比只做 2-3 个候选的风险、当前价格/净值、费率、流动性、回撤和适用人群横向决策，
  不生成组合比例，也不附带购买指令。

推荐只做展示，不会自动下单。用户需要明确回复“购买第几只”或产品名称，再补充金额和
付款银行卡；系统随后展示确认页，验证付款卡交易密码，大额交易继续验证短信验证码。
申购完成后会同步扣减银行卡余额、生成交易流水与持仓，并刷新银行卡资产总额。

生日惊喜采用“先推荐、后购买”流程：如果画像或关心的人资料里已有生日，系统会直接使用，
不再重复要求输入；随后逐项补充喜好、过敏或禁忌、预算，再生成 3 组礼物方案。
用户可以回复“换一批”继续浏览，只有明确选择某个方案并再次确认后，才会锁定生日专款
并创建生日前 2 天的礼物预约。花粉、乳制品等禁忌会过滤鲜花和蛋糕，并补充相册、饰品、
手作体验等非食品类礼物。推荐和最终预约单使用具体商品名，例如“定制相册”“银饰礼盒”
“双人手作体验”，不使用“心意礼物”“精选礼物”这类抽象营销标签。
需要到淘宝核价的兴趣类礼物会先展示同类商品的市场参考区间，例如“参考 ¥60-¥180”，
再提供淘宝搜索入口；参考价只用于预算判断，不冒充实时售价或库存。

风险测评完成后，评级、分值和测评时间会写回客户画像；资料页修改的卡名、备注和开关
会立即被对话端、转账工具和理财付款卡选择器读取，不需要重新创建会话。

财务健康分使用 0-100 分分段基准映射：应急金参考 3-6 个月必要支出、信用卡使用率参考
低于 30%、储蓄率参考 20%、资产类别参考至少 4 类、订阅负担参考低于月收入 8%。
每个维度同时返回当前值、参考标准、得分状态和预计可提升分数；建议包含原因、目标、
行动步骤和优先级。该模型是原型评分，不替代监管信用评分或银行授信审批。

账务对账用于发现“卡片展示余额、底层关联账户、总资产函数”之间的差异，常见来源包括
手工改卡、重复导入和历史数据迁移。发现差异后，用户可以选择“以银行卡余额为准”或
“以关联账户余额为准”进行人工修正；修正需要二次确认并写入审计日志。修复完成后页面展示
卡账和账户的修正前后金额，并提供“重新核对”入口。

每日简报不会再直接生成。首次请求先展示必选/可选材料清单，并提供账单上传、文本粘贴和
“使用当前已接入数据生成”三个入口；只有确认材料后才生成风险、订阅、待办和目标摘要。

### 6.1 数据提供与持久化边界

业务工具通过 `ToolContext.providers` 获取数据，不在工具里直接决定“默认账户”或散落 Mock 查询：

- `accounts`、`transactions`、`cards`、`wealth`、`subscriptions`、`merchants` 都有独立 Provider；
- `bank` 是 `DemoBankAdapter` 沙箱边界，后续可替换为 Open Banking/银行沙箱实现；
- 每条账户、流水、卡片、订阅、产品、持仓和商户报价都带 `source`、`updated_at`、`is_live`、`is_demo`；
- 行情 Provider 带 60 秒缓存、最小请求间隔、失败冷却、重试、腾讯/东方财富主备源和陈旧标记；
- SQLite 的 `accounts`、`transactions`、`upload_batches`、`cards`、`subscriptions`、`holdings`、`tasks`、`audit_logs` 等表与 JSON 快照同步写入，便于查询、审计和重启恢复。

腾讯财经和东方财富被定位为**公开数据增强**，不是生产级行情源；没有行情时只展示明确标注的演示参数。

### 6.2 统一沙箱与回调状态机

`finagent/integrations/sandbox_adapters.py` 为银行、支付和券商提供同一套执行协议：

- `bank`：账户同步、卡片生命周期、本人卡互转；
- `payment`：对外转账、AA 收款、账单支付；
- `broker`：模拟交易柜台，支持申购、赎回和订单状态。

每次执行都会持久化到 `sandbox_executions`，并记录
`submitted → processing → completed / failed / returned / reversed` 的轨迹。
完成后仍可由签名回调推进到退回或冲正；支付退回会恢复付款账户余额，相同回调幂等，
非法状态迁移会拒绝。API：

```text
GET  /v1/sandbox/status?session_id=...
POST /v1/sandbox/callbacks
GET  /v1/market/status?session_id=...
```

回调使用 `X-FinAgent-Signature` 请求头，签名密钥复用 `FINAGENT_WEBHOOK_SECRET`。

### 6.3 持牌行情与模拟交易柜台

配置以下环境变量后，行情路由会优先调用持牌 REST 网关，未返回的标的再回退公共行情：

```text
FINAGENT_LICENSED_MARKET_URL=https://vendor.example/api
FINAGENT_LICENSED_MARKET_KEY=...
FINAGENT_LICENSED_MARKET_NAME=licensed-vendor
```

网关只需把供应商字段归一化为 `quotes` 和 `nav` 两组 JSON。未配置凭证时，
`/v1/market/status` 会明确显示 `public-data-enhancement`，不会声称已接入持牌数据。
理财申购和赎回通过 `BrokerSandboxAdapter` 的模拟交易柜台执行，不向真实券商发送订单。

## 十四、扩展指南

### 新增一个业务工具（三步）

1. 写一个 `Tool` 子类（建议按业务域放到对应的 `tools/*.py`）：

```python
class ExchangeRateTool(Tool):
    name = "forex.rate"
    category = "跨境服务"
    description = "查询汇率并试算换汇金额"
    params = [
        ToolParam("currency", "string", True, "外币代码，如 USD"),
        ToolParam("amount", "number", False, "换汇金额（元）"),
    ]

    def run(self, ctx, currency, amount=None):
        ...
        return ToolResult(True, "...", data={...})
```

2. 在 `finagent/agent/registry.py` 的 `build_default_registry()` 里注册一行；
3. 在 `finagent/nlu/intent_schema.py` 加一条 `IntentSpec`，并在
   `finagent/agent/planner.py` 的 `SIMPLE_PLANS` 里加一条映射。

### 新增一个场景

- **多步场景**：在 `Planner` 里加一个 `_xxx_plan()` 方法，返回多个 `PlanStep` 即可，
  参考 `_birthday_plan()`。
- **调整风控**：只改 `config.py` 的 `RiskPolicy` 或 `risk/engine.py`，其它模块不用动。
- **调整风险测评**：改 `finagent/risk/scorecard.py` 里的打分项与阈值即可，
  评分卡是纯配置化的，新增一个维度不需要动推荐和适当性代码。
- **接入新的 OCR 引擎**：在 `finagent/vision/receipt_reader.py` 里加一个
  `_from_xxx()` 方法并挂进 `read()` 的优先级链，解析部分可以复用
  `receipt_parser.parse_receipt_text()`。
- **换数据源**：实现 `BankAdapter` 或替换 `build_data_providers()` 的 Provider，
  工具层仍然只消费统一接口；生产部署再替换公开行情源和 SQLite 投影。

## 十五、已知限制与后续规划

| 限制 | 说明 |
|------|------|
| 仍是原型事务边界 | SQLite 已保存会话、账户、持仓、任务和审计投影，但未实现生产级连接池、分布式锁和完整事务编排 |
| 验证码是固定值 | 演示环境固定 `123456` |
| 无真实对接 | 不接征信、支付通道、银行核心系统；目前使用可控的银行沙箱适配器 |
| 意图清单是白名单 | 规则与 LLM 都只认已登记的意图，超出范围会引导用户换个说法 |
| 订阅识别是启发式 | 基于金额稳定性与扣费间隔，不是商户协议数据库 |
| OCR 有误差 | Windows 离线 OCR 对清晰截图识别率尚可，但版式复杂的真实截图建议走多模态模型；识别结果一律先让用户核对再入库 |
| 风险测评为内置评分卡 | 不是监管要求的完整问卷，也不含问卷答案校验、录音录像等流程 |

后续可以做的方向：接入真实风险测评问卷、把意图识别换成 function calling、
加多用户会话隔离、把工具调用轨迹做成可视化面板。
